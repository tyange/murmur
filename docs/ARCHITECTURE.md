# murmur 아키텍처

> 상태: **승인됨 (2026-09-29)**. D1~D4 결정 완료. 결정 항목은 `✅ 결정`으로 표시하고 이유를 함께 기록한다.

murmur는 사용자의 로컬 머신에서 동작하는 초경량 트위터형 마이크로블로그다. 데이터를 소유하는 중앙 서버가 없고, 사용자의 기기끼리, 그리고 (옵트인 시) 사용자끼리 P2P로 연결된다.

---

## 1. 핵심 원칙

모든 설계 결정은 아래 원칙에 비춰 판단한다. 원칙과 충돌하는 편의 기능은 넣지 않는다.

| # | 원칙 | 설계상 귀결 |
|---|------|-------------|
| P1 | 데이터를 소유하는 중앙 서버는 없다 | 상시 켜진 노드(VPS 등)도 "사용자의 기기 중 하나"로 취급한다. 특별한 권한이 없다. |
| P2 | 서명 키는 사용자 기기에만 존재한다 | 노드·호스트는 **서명된 이벤트를 저장·전달만** 한다. 모든 수신 측은 서명을 스스로 검증한다. 호스트가 거짓말할 수 있는 것은 "무엇을 안 보여주는가"뿐이다. |
| P3 | 기본은 "내 기기끼리만" | 네트워크 기능은 기본적으로 같은 신원(identity)의 기기만 받아들인다. 타 유저 연결·공용 토픽은 명시적 설정으로만 켜진다. |
| P4 | 모든 글은 서명된 이벤트 | P2P 프로토콜과 공개 API가 **같은 바이트 형식**의 이벤트를 주고받는다. 변환 계층이 없다. |
| P5 | 데몬은 선택, 키 소유는 필수 | 코어는 라이브러리다. CLI는 데몬이 있으면 API 클라이언트, 없으면 코어를 내장해 단독 실행한다. |
| P6 | 초경량 | 의존성 추가 시 이유를 기록한다(§9). 기능 플래그로 단계별 의존성을 분리한다. |

## 2. 워크스페이스 구조

```
murmur/
├── Cargo.toml            # workspace
├── crates/
│   ├── core/             # murmur-core: 이벤트 모델, 서명, 저장, 동기화, 네트워킹
│   ├── daemon/           # murmur-daemon: 상시 실행 + API (2단계~)
│   └── cli/              # murmur (바이너리): CLI/TUI
├── web/                  # SolidJS PWA (5단계)
└── docs/
```

`core` 내부 모듈(1단계 기준):

```
core/src/
├── lib.rs
├── keys.rs      # 신원 키, 기기 키, 위임 인증서
├── event.rs     # 이벤트 구조, 정규 직렬화, 서명·검증
├── store.rs     # SQLite 저장소 (이벤트 로그, 기기 목록, 동기화 커서)
├── sync.rs      # 동기화 프로토콜 (전송 무관 로직: 무엇을 주고받을지)
└── net.rs       # libp2p Swarm 구성 (mDNS + 동기화 프로토콜)
```

`sync.rs`(무엇을 주고받는가)와 `net.rs`(어떻게 전달하는가)를 분리하는 이유: 동기화 병합 로직을 네트워크 없이 단위 테스트할 수 있고, 4단계 공개 API(HTTP)가 같은 로직을 재사용할 수 있다.

## 3. 신원과 키 모델

### 3.1 구조

```
Identity Key (ed25519)  ── 사용자 = 이 공개키
   │  위임 서명 (DeviceCert)
   ├── Device Key A (ed25519)  ── 노트북
   ├── Device Key B (ed25519)  ── VPS 노드
   └── Device Key C (ed25519)  ── (폐기됨)
```

- **신원 키**: 사용자 식별자. 공개키 자체가 ID다(표시용으로 base32/bech32 등 인코딩). 평소 글 서명에는 쓰지 않는다. 쓰임새는 오직 **기기 위임과 기기 폐기**.
- **기기 키**: 기기마다 생성, 그 기기 밖으로 나가지 않는다. 모든 글은 기기 키로 서명한다.
- **DeviceCert**: 신원 키가 기기 키에 서명한 위임 인증서.

```rust
struct DeviceCert {
    identity: PublicKey,     // 위임하는 신원
    device:   PublicKey,     // 위임받는 기기
    label:    String,        // "macbook", "vps" 등
    issued_at: u64,          // unix ms
    sig:      Signature,     // identity가 위 필드들에 서명
}
```

### 3.2 검증 규칙

이벤트 `e`가 유효하려면:
1. `e.sig`가 `e.device` 공개키로 검증된다.
2. `e.device`에 대해 `identity == e.author`인 유효한 DeviceCert가 존재한다.
3. 해당 기기가 폐기되지 않았거나, 폐기 정책(§3.4)상 여전히 인정되는 이벤트다.

### 3.3 신원 키 보관 — ✅ 결정: 첫 기기 + 복구 시드 (D4)

- 신원 키는 `murmur init`을 실행한 첫 기기에 저장한다. 기기 추가·폐기는 이 기기에서만 할 수 있다.
- `init` 시 신원 키 시드(32바이트)를 **base32 복구 문자열로 한 번만** 출력한다. 사용자가 적어 둔다.
- `murmur init --recover <시드>`로 다른 기기에서 신원 키를 복원할 수 있다. 복원한 기기가 새 "신원 기기"가 된다(새 기기 키를 자기 인증서로 발급).
- 복구 문자열을 가진 사람은 신원 전체를 가진 것과 같다. 출력 시 경고를 표시한다.
- BIP39 단어 니모닉은 의존성이 생기므로 이후 단계에서 검토한다(같은 32바이트 시드의 다른 표현일 뿐이라 호환 가능).

### 3.4 기기 폐기와 전파 — ✅ 결정: 서명 이벤트 + seq 기준 (D3)

```rust
struct DeviceRevoke {
    identity: PublicKey,
    device:   PublicKey,   // 폐기 대상
    last_valid_seq: u64,   // 이 seq까지는 정상 글로 인정, 초과분은 무효
    issued_at: u64,
    sig:      Signature,   // identity 키로 서명 (도메인 접두사 b"murmur-revoke-v1")
}
```

- **전파**: DeviceCert·DeviceRevoke도 이벤트와 같은 경로(합집합 동기화)로 퍼진다. 별도 메커니즘이 없다. 한 번 받은 폐기는 되돌리지 않는다.
- **판정**: 기기 X가 폐기되면 X의 이벤트 중 `seq <= last_valid_seq`만 유효하다. `created_at`은 작성자가 주장하는 값이라 판정에 쓰지 않는다.
- `last_valid_seq`는 폐기를 서명하는 기기가 "내가 본 X의 최대 연속 seq"로 기본 설정하고, 사용자가 조정할 수 있다.
- 폐기를 늦게 받는 경우: 이미 저장한 `seq > last_valid_seq` 이벤트는 폐기를 받는 시점에 무효 처리(숨김)한다. 원본은 증거로 남긴다.
- 같은 신원에 대해 같은 기기의 폐기가 여러 개면 `last_valid_seq`가 **가장 작은 것**이 이긴다(보수적 병합, 순서 무관).
- 한계: 폐기를 아직 받지 못한 노드는 그동안 도난 키의 글을 받아들인다. P2P 구조상 피할 수 없는 결과적 일관성이다.

### 3.5 페어링 (1단계 범위)

1단계는 텍스트 코드 복사·붙여넣기로 한다. QR은 같은 페이로드를 QR로 인코딩하는 것뿐이라 나중에 얹는다.

```
[새 기기]   murmur init --join          → 기기 키 생성, "가입 요청 코드" 출력 (device pk + label)
[신원 기기] murmur device add <요청코드> → DeviceCert 서명, "인증서 코드" 출력
[새 기기]   murmur device accept <인증서코드> → 인증서 저장, 이제 동기화 가능
```

코드에는 비밀이 없다(공개키와 서명뿐). 코드를 가로채도 새 기기의 비밀키는 얻을 수 없다. 단, 사용자는 요청 코드가 "내 새 기기에서 온 것"임을 눈으로 확인해야 한다(짧은 지문 표시).

## 4. 이벤트 데이터 모델

### 4.1 공통 봉투 (Envelope)

```rust
struct Event {
    // --- 서명 대상 ---
    v:          u8,            // 형식 버전 = 1
    author:     PublicKey,     // 신원 공개키
    device:     PublicKey,     // 서명한 기기 공개키
    seq:        u64,           // 해당 device의 단조 증가 번호 (1부터)
    created_at: u64,           // unix ms, 작성자 주장값 (신뢰하지 않음, 정렬용)
    kind:       Kind,
    body:       Body,          // kind별 내용
    // --- 서명 대상 아님 ---
    sig:        Signature,     // device 키로 서명
}
// id = hash(서명 대상 정규 바이트)  → 내용 주소. 저장 키, 참조(답글) 키로 사용.
```

- `id`는 필드로 저장하지 않고 계산한다. 누구도 id와 내용을 어긋나게 만들 수 없다.
- `seq`는 동기화 커서를 단순하게 만든다(§6.2). 같은 device가 같은 seq로 서로 다른 이벤트를 서명하면 **equivocation**(키 오용 증거)으로 기록하고 둘 다 보관·표시 보류한다.
- 서명 대상 CBOR 배열의 **첫 원소에 도메인 문자열**(`"murmur-event-v1"`, 인증서는 `"murmur-cert-v1"`, 폐기는 `"murmur-revoke-v1"`)을 넣어, 같은 키로 서명하는 다른 메시지(DeviceCert, libp2p 핸드셰이크 등)와 절대 혼동되지 않게 한다.

### 4.2 Kind (1단계)

| kind | body | 비고 |
|------|------|------|
| `post` | `{ text: String }` (최대 길이 제한, 예: 500자) | 불변 |
| `delete` | `{ target: EventId }` | 같은 author만 유효. 원본 이벤트는 남기고 표시만 숨김(tombstone) |

`reply`, `repost`, `profile`, `follow` 등은 해당 단계에서 추가한다. `Kind`는 알 수 없는 값을 **보존하고 무시**하도록 설계해, 구버전 노드가 신버전 이벤트를 깨뜨리지 않고 전달할 수 있게 한다.

### 4.3 직렬화 형식 — ✅ 결정: 결정적 CBOR (D1)

서명은 "정규(canonical) 바이트"에 대해 이뤄져야 한다. 같은 이벤트는 누가 언제 인코딩해도 같은 바이트가 나와야 한다.

- 형식: CBOR (RFC 8949), 결정적 인코딩 규칙(§4.2.1: 최단 길이 정수, 무한 길이 항목 금지)을 따른다.
- 서명 대상은 **순서가 고정된 CBOR 배열**로 인코딩한다: `[v, author, device, seq, created_at, kind, body]`. 맵을 쓰지 않으므로 키 정렬 문제가 없다.
- 공개키·서명은 CBOR byte string(major type 2)으로 그대로 담는다.
- 보장 방법: 인코딩 → 디코딩 → 재인코딩 바이트 동일성 테스트, 비정규 입력(긴 정수 표기 등) 거부 테스트.
- 이유: 바이너리 네이티브·표준·JS 라이브러리 존재로 P4(P2P와 공개 API의 같은 형식)를 만족한다. JCS 대비 base64·u64 정밀도 함정이 없고, postcard 대비 타 언어 접근성과 스키마 진화가 낫다.

## 5. 저장 (SQLite)

1단계 스키마 초안:

```sql
events(id BLOB PK, author BLOB, device BLOB, seq INTEGER, created_at INTEGER,
       kind TEXT, raw BLOB,              -- raw = 서명 포함 원본 바이트 (재전송 시 그대로 보냄)
       received_at INTEGER,
       UNIQUE(device, seq))
devices(device BLOB PK, identity BLOB, label TEXT, cert BLOB,
        revoke BLOB NULL, last_valid_seq INTEGER NULL)
local_keys(role TEXT PK, secret BLOB)    -- 'device', 'identity'(신원 기기에만)
```

- **원본 바이트(`raw`)를 그대로 저장·전달**한다. 재인코딩하면 서명이 깨질 위험이 있다. 인덱스 컬럼은 파생값일 뿐이다.
- 비밀키 저장: 1단계는 파일 권한(0600) + SQLite 파일로 시작하고, OS 키체인 연동은 이후 검토한다.
- 데이터 디렉터리: 기본 OS 데이터 경로, `--home <dir>`로 변경 가능(같은 머신에서 두 "기기"를 띄워 테스트하는 용도).

## 6. 동기화

### 6.1 무엇을 동기화하는가

| 데이터 | 성격 | 병합 방식 |
|--------|------|-----------|
| 서명된 이벤트(글, 삭제) | 불변, 추가만 | **집합 합집합** (grow-only set). 이미 CRDT다. |
| 기기 목록(Cert, Revoke) | 추가만 | 합집합. 폐기는 한 번 적용되면 되돌리지 않음. |
| 가변 개인 상태(향후 팔로우 목록, 프로필 등) | 가변, 동시 편집 | automerge — **1단계에는 없음** (D2) |

서명된 이벤트는 불변이므로 병합 충돌이 원리적으로 없다. CRDT(automerge)가 실제로 필요한 곳은 "여러 기기에서 동시에 수정되는 가변 상태"뿐이다.

**✅ 결정 (D2)**: 글·삭제·기기 목록은 서명 이벤트의 합집합(grow-only set)으로 동기화한다. 이것이 로드맵 1단계의 "CRDT 동기화"다. automerge는 가변 상태(팔로우 목록 등)가 처음 생기는 단계에 도입하며, 그때도 문서는 기기 간(자기 신원 내부)에서만 동기화하고 제3자 호스트에 맡기지 않는다. 이유: automerge change에는 murmur 서명이 없어, 글을 automerge에 담으면 호스트가 위조 변경을 섞을 수 있다(P2 위반). 1단계에서 빼면 의존성도 줄어든다(P6).

### 6.2 이벤트 동기화 프로토콜 (제안)

기기별 `seq`가 있으므로 상대가 가진 것을 **버전 벡터** 하나로 요약할 수 있다.

```
A → B : Have { device_a: 42, device_b: 17, device_c: 3 }   // 각 기기별 최대 연속 seq
B → A : Events [ B가 가진 것 중 A의 벡터보다 새로운 raw 이벤트들 ]
(양방향으로 한 번씩)
```

- 수신 측은 모든 이벤트를 §3.2 규칙으로 **개별 검증 후** 저장한다. 상대가 내 기기라도 검증을 생략하지 않는다(P2).
- seq에 구멍이 있으면(예: 1..10, 12) "최대 연속 seq"=10을 보고해 11을 다시 받는다.
- 이벤트 수가 커지면 범위 기반 집합 조정(range-based set reconciliation)으로 교체할 수 있도록 `sync.rs` 인터페이스를 좁게 유지한다.

### 6.3 전송 (1단계)

- libp2p: TCP + Noise + Yamux, mDNS로 같은 LAN의 피어 발견.
- 동기화는 libp2p `request_response` 프로토콜(`/murmur/sync/1`)로 구현.
- 연결 직후 서로의 DeviceCert를 교환해 **같은 identity가 아니면 연결을 끊는다**(P3). mDNS는 LAN의 다른 murmur 사용자도 발견하므로 이 필터가 필수다.
- 1단계 동기화 트리거: `murmur sync` 명령이 일정 시간 동안 Swarm을 띄우고 발견된 내 기기와 동기화 후 종료. (상시 동기화는 2단계 데몬의 일)

**PeerId = 기기 키 (D4)**: 기기 키(ed25519)를 그대로 libp2p `Keypair`로 쓴다. Noise 핸드셰이크가 "연결 상대가 이 기기 키의 소유자"임을 이미 증명하므로, 연결 후 상대의 DeviceCert만 받아 `cert.device == 상대 PeerId의 공개키`이고 `cert.identity == 내 identity`인지 확인하면 된다. 키 재사용이지만 libp2p는 `"noise-libp2p-static-key:"`, murmur는 `"murmur-*-v1"` 도메인 접두사로 서명하므로 서명이 서로 재사용될 수 없다.

## 7. 단계별 경계

각 단계는 이전 단계의 코드를 **확장만** 하고 이벤트 형식은 바꾸지 않는 것을 목표로 한다. 형식 변경이 필요하면 `v`를 올린다.

| 단계 | 범위 | 명시적으로 **하지 않는 것** |
|------|------|-----------------------------|
| **1. 코어 + CLI** | 키 생성, 페어링(텍스트 코드), 기기 폐기, 글 작성·서명·저장, 삭제, 로컬 타임라인, mDNS 내 기기 동기화, `murmur sync` 1회성 실행 | 데몬, API, 인터넷 너머 연결, 타 유저, TUI(1단계는 평문 출력) |
| **2. 데몬 + 소유자 API** | 상시 실행, localhost 토큰 인증 API + WebSocket, CLI의 API 모드, Kademlia·identify·autonat·relay·dcutr로 인터넷 너머 내 기기 동기화, ratatui TUI | 타 유저 연결, 공개 API |
| **3. 유저 간 소통** | 공개키 기반 1:1 연결, 공용 토픽 gossipsub, 신뢰망·작업증명 스팸 필터, reply/follow 등 kind 추가 | 공개 API |
| **4. 공개 API + 호스팅** | 서명 이벤트 제출·조회 HTTP API(요청량 제한), 데몬 없는 사용자의 이벤트 대리 저장·전파 | — |
| **5. 웹 UI** | SolidJS PWA, 데몬이 서빙, 모바일 복제본 | — |

단계 경계에서 의존성도 끊는다. 예: `axum`은 daemon 크레이트에만, libp2p의 kad/relay/dcutr 기능은 2단계에서 feature로 추가한다.

## 8. 테스트 전략

- **서명·검증**(core): 정상 서명 통과 / 필드 1비트 변조 시 실패 / 위임 없는 기기 키 거부 / 다른 identity의 cert 거부 / 폐기된 기기 처리 / 도메인 분리(cert 서명을 이벤트 서명으로 재사용 불가).
- **직렬화**: 인코딩→디코딩→재인코딩 바이트 동일성, 알 수 없는 kind 보존.
- **동기화 병합**(sync.rs, 네트워크 없이): 두 저장소 간 교환 후 동일 집합 / 교환 순서 무관 / 중복 수신 멱등 / seq 구멍 복구 / 위조 이벤트 섞였을 때 해당 이벤트만 거부.
- **통합**: 같은 프로세스에서 두 Swarm을 띄워 mDNS 없이 직접 dial → 동기화 확인.

## 9. 의존성과 그 이유 (1단계)

| 크레이트 | 이유 |
|----------|------|
| `ed25519-dalek` | 서명. 표준, 순수 Rust, 감사됨. `rand_core` feature는 끄고 키는 `getrandom`으로 만든 시드에서 생성 |
| `getrandom` | OS 난수(키 시드). 3.0의 `generate()`도 결국 getrandom의 `SysRng`를 요구하므로, rand_core 트레이트를 거치지 않고 32바이트를 직접 채운다 |
| `rusqlite` (bundled) | 단일 파일 저장소, 시스템 SQLite 의존 제거 |
| `serde` | 직렬화 공통 인터페이스 |
| `ciborium` | 결정적 CBOR 직렬화 (D1). serde 기반, 순수 Rust |
| `sha2` | 이벤트 id 해시(SHA-256). ed25519-dalek이 이미 내부적으로 의존하므로 실질 추가 비용 없음 |
| `data-encoding` | base32 (복구 시드, 페어링 코드, 공개키 표시). 의존성 없는 작은 크레이트 |
| `libp2p` (tcp, noise, yamux, mdns, request-response, tokio) | 1단계 네트워킹. 필요한 feature만 켠다 |
| `tokio` | libp2p 런타임 |
| `clap` | CLI 파싱 |
| ~~`automerge`~~ | 1단계 제외 (D2). 가변 상태가 생기는 단계에서 추가 |

## 10. 결정 기록 (선택지와 트레이드오프)

### D1. 이벤트 직렬화 형식 — ✅ 결정: 결정적 CBOR (§4.3)

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **A. 정규 JSON (RFC 8785 JCS)** | 사람이 읽음, 웹 UI·공개 API에서 그대로 사용, 디버깅 쉬움 | 바이너리(키·서명)를 base64 등으로 인코딩해야 함, 숫자 정규화 함정(u64가 JS에서 정밀도 손실), 크기 큼 |
| **B. 결정적 CBOR (RFC 8949 §4.2)** | 바이너리 네이티브, 작음, 표준, JS 라이브러리 존재 | 사람이 못 읽음, "결정적" 규칙을 라이브러리가 제대로 지키는지 검증 필요 |
| **C. 고정 순서 바이너리 (postcard/bincode류)** | 가장 작고 빠름, 필드 순서 고정이라 정규성 자연 확보 | Rust 밖(웹, 타 구현)에서 다루기 어려움, 스키마 진화가 까다로움 |
| **D. 서명은 고정 바이너리 / 전송은 JSON** | 서명 안정성 + API 가독성 | 형식이 둘 → P4("같은 형식")에 어긋남, 변환 버그 위험 |

### D2. CRDT(automerge) 문서 단위 — ✅ 결정: 가변 상태만, 1단계 제외 (§6.1)

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **A. 서명 이벤트 = 집합, automerge는 가변 개인 상태에만** | 글은 이미 CRDT(합집합)라 automerge 불필요, 모든 글이 개별 서명돼 호스트 위조 불가(P2), 가벼움 | automerge를 쓰는 곳이 작아 1단계엔 사실상 사용처가 없을 수 있음 |
| **B. 사용자당 automerge 문서 1개에 모든 글 포함** | 동기화 구현이 automerge sync 하나로 끝남 | automerge 변경(change)에는 **우리 서명이 없음** → 제3자 호스트(4단계)가 위조 변경을 섞을 수 있음, 문서가 계속 커짐, P4의 "이벤트 형식 공유"와 어긋남 |
| **C. 글마다 automerge 문서** | 글 수정·공동 편집 가능 | 문서 수 폭증, 트위터형에 과함 |

추가 질문: A를 고르면 **1단계에서 automerge를 아예 빼고** 필요해지는 단계(예: 팔로우 목록 동기화)에 넣을지.

### D3. 기기 키 폐기 전파 — ✅ 결정: 서명 이벤트 + seq 기준 (§3.4)

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **A. 폐기 = 일반 서명 이벤트, 합집합 동기화로 전파** | 추가 메커니즘 없음, 한 번 받으면 영구 | 폐기를 아직 못 받은 노드는 도난 키의 글을 받아들임(결과적 일관성) |
| **B. 신원 키가 서명한 "기기 목록" 문서(버전 번호), 최신 버전이 이김** | 현재 유효 기기 집합이 명확, 검증 간단 | 목록을 매번 통째로 재서명, 신원 키가 자주 필요 |

A/B 공통으로 정해야 할 **폐기 이전 글 처리**:
- (i) `effective_at` 이후 `created_at`인 글만 무효 — 도난 키로 과거 시각을 주장하면 뚫림.
- (ii) 해당 기기의 **특정 seq 이후**만 무효 — 신원 기기가 "내가 마지막으로 본 seq"를 폐기에 박음. 시각 위조에 강함. (제안)
- (iii) 해당 기기의 모든 글 무효 — 가장 안전, 정상 글도 사라짐.

### D4. 신원 키 보관 + libp2p 키 — ✅ 결정: 첫 기기 + 복구 시드, PeerId = 기기 키 (§3.3, §6.3)

신원 키 위치:

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **A. 첫 기기에 보관** | 단순, 기기 추가·폐기 바로 가능 | 그 기기를 잃으면 신원을 복구할 방법이 없음 |
| **B. 첫 기기에 보관 + 생성 시 복구 문구(BIP39류 니모닉) 출력** | 기기 분실에도 신원 복구 가능 | 의존성 추가(워드리스트), 사용자가 문구를 관리해야 함 |
| **C. 생성 직후 오프라인 백업으로 내보내고 기기에서 삭제** | 가장 안전 | 기기 추가마다 백업을 꺼내야 함, 초경량 UX와 충돌 |

libp2p PeerId:
- **a. 기기 키를 그대로 libp2p 키로 사용** — PeerId = 기기 공개키라 별도 바인딩 불필요, 연결 상대가 곧 cert의 device. 키 재사용이지만 libp2p 핸드셰이크 서명과 이벤트 서명은 접두사가 달라 혼동 불가.
- **b. 별도 libp2p 키, cert 교환 시 기기 키로 PeerId에 서명해 바인딩** — 키 분리 원칙에 충실, 바인딩 단계 하나 추가.
